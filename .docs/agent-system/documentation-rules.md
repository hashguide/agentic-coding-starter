# Documentation Rules

## Place information at the right authority level

- Reusable selection guidance → `playbook/`
- Product-wide requirement or decision → `project/`
- One capability's required behavior → `features/<feature>/`
- Consequential choice with alternatives and consequences → `decisions/`
- Current work and progress → `execution/`
- Review evidence and findings → `validation/`

## Keep project truth current

Update documentation in the same change when behavior, architecture, data shape, permissions, public contracts, user flows, or operational requirements change.

## Prefer durable facts

Project docs should record the chosen behavior, rationale where useful, constraints, and consequences. Exploratory discussion belongs in working notes or decision records rather than authoritative requirements.
